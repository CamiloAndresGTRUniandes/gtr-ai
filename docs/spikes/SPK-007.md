# SPK-007 — SQLite persistence

**Status:** OPEN — partial Apply/Verify evidence; not closed

## Technical question
Can the proposed SQLite persistence satisfy the master prompt requirements?

## Verified results
In the retained WSL2 run, `sqlite-native` passed (exit `0`), showing FTS5 and rollback in a limited `node:sqlite` smoke test (SQLite `3.54.1`). The `sqlite-vector` test failed (exit `1`) because vector IDs must be integers. No successful vector run is present in the retained raw logs.

## Reported results awaiting independent reproduction
Verify reported that the corrected smoke test loaded `sqlite-vec` `0.1.9` with both `node:sqlite` and `better-sqlite3` `13.2.0`, matched FTS5, inserted synthetic vectors using integer-compatible row IDs, and returned the expected nearest row. Verify also reported a warm p95 of approximately `0.0116 ms` over 1,000 synthetic queries per binding. No committed raw success or timing log supports these reports. The timing is a reported synthetic smoke-test observation, not a workload benchmark.

## Remaining acceptance criteria and limitations
Migration and backup/restore behavior with the selected binding, disk-scale concurrency, LangGraph checkpoint compatibility, native Windows/Linux/macOS behavior, and a single supported binding strategy remain unverified. LangGraph resolved nested `better-sqlite3` 12.11.1 via `@langchain/langgraph-checkpoint-sqlite` requiring `^12.10.0`, distinct from direct 13.2.0, so the evidence does not establish one shared binding.

## Recommendation / fallback
Evaluate `node:sqlite` first for the target runtime, but defer selection until checkpoint, vector extension and OS matrix tests complete.

## Security and licensing
No credentials, paid requests or external writes were used. Extension integrity, install scripts and transitive licenses require review.
